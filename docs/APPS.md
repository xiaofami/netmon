# 服务识别与隐私观察

对应前端「流量排行」「隐私观察」两个视图，实现在 `src/netmon-report.c`：
服务分类逻辑与 `emit_traffic()` / `emit_privacy()` 都在这个文件里
（早期曾拆出 `src/apps.c`，后来合回，以免采集侧和报表侧各存一份分类表）。

---

## 一、服务识别：为什么不用现成的 DPI 库

调研过主流开源方案：

| 库 | 语言 | 协议数 | 原理 | 结论 |
|---|---|---|---|---|
| **nDPI** | C / LGPLv3 | 250+ | 报文载荷 + TLS 证书 / SNI + 端口 | 成熟活跃，但要**抓全量报文** |
| **libprotoident** | C++ / GPLv2 | 200+ | 只看每方向载荷前 4 字节 | 轻量，但同样要抓包 |
| OpenDPI / L7-filter | C | ~100 | 载荷正则 | 项目已停止维护，不考虑 |
| NFStream | Python | 依赖 nDPI | 同 nDPI | Python 运行时，不适合路由器常驻 |

**没有采用**，原因不是它们不好，而是架构不匹配：

- netmon 的连接数据来自只读 `/proc/net/nf_conntrack` 的**累计字节计数**，
  没有报文载荷；AF_PACKET 嗅探器用经典 BPF 只放行 `udp/53`，只看 DNS。
- 为识别服务去抓全量报文，等于把「被动旁路、零数据面开销」推翻，
  还会带来内存、CPU 和隐私（读用户报文内容）三方面的新问题。

因此用**纯元数据三层特征**，全部来自已有记录，零额外抓包：

1. **域名关键词**：`netmon-report.c` 里的 `SIGS[]` 表，覆盖抖音/快手/B站/爱奇艺/
   萤石/群晖/Windows 更新/BT tracker/微信/淘宝等，约 30 组。
2. **目的端口**：`PORTS[]` 表，1935 RTMP、554 RTSP、6881 等 BT 端口、
   1194/51820 VPN、5228 推送、443/80 网页等。域名没命中时才用。
3. **上下行比例**：`bytes_out / bytes_in`，前端据此提示
   「上行大 = 上传/直播推流/PT 做种，下行大 = 观看/下载」。

匹配顺序即表顺序（越具体越靠前），新增服务只要加一行，不动逻辑。
**这是推测不是 DPI 判定**：手机 App 普遍共用 CDN 域名，
「其他 / 网页」偏多属正常，界面已如实标注。

### 输出字段

- `traffic_hosts[]`：域名或目的 IP + 服务名 + 大类 + 连接数 + 上/下行字节
- `app_stats[]`：按服务大类汇总的连接数、流量、占比
- 设备流量排行直接用 `devices[]` 现有的 `bytes_in/bytes_out/conns` 前端排序

## 二、隐私观察：能不能监控到「内置录屏上传」

### 事件背景（2026 年公开报道）

开发者对搭载 HyperOS 3 的小米 14 做逆向，指出两个预装组件：

| 组件 | 行为 | 上报端点 |
|---|---|---|
| `com.miui.guardprovider`（系统安全组件） | 约每 5 秒录 3 秒屏 → 720p MP4 → Base64 + 加密 POST；判定无风险则删除，间隔 2 秒继续 | 厂商反诈云 |
| `com.mobiletools.systemhelper`（联通组件） | 已装 App 列表、近 24h 使用时长、流量消耗 + IMEI/IMSI/ICCID；不限运营商 | `dm.wo.com.cn:18080/register` |

报道称涉及小米、OPPO、vivo、一加、三星、真我、努比亚、中兴等，
华为与荣耀未在名单内；小米官方文档确有「设备涉诈检测」能力说明。
用户侧公开的处置方式包括 ADB 对当前用户卸载组件、或 hosts 拦截上报域名。

### 我们能看到 / 看不到

**能看到**：每台设备发起的 DNS 域名、每条连接的目的地址与端口、
上下行字节数、持续时间、发生时间。所以可以发现：

- 某台设备在后台持续向少数固定地址发送小体积上行，时间分布规律；
- DNS 查询命中已知上报 / 遥测域名。

**看不到**：报文加密，读不到画面内容，也无法把某次上传直接定性为录屏。
云相册备份、网盘/微信自动同步、应用日志打点会有几乎一样的形态。

### 检测设计（严格判定 + 原始观察，分开呈现）

**严格判定 `suspects`**（满足全部条件才算疑似）：

```
单条上行 50KB ~ 8MB          （3 秒 720p MP4 的量级）
连接 15 秒内结束              （小片上传，不是长连接）
回应流量 < 上行 / 4           （上传为主）
同一源地址 ≥ 40 次            （周期性反复）
```

SQL 在 `emit_privacy()`，输出源 IP、次数、上行总量、目标去重数。

**原始观察 `watch`**：只按设备统计上行连接数 / 上行总量 / 目标数，
**不做任何判定**。严格判定为空时用户仍能看到趋势。

**域名线索 `telemetry`**：`apps_is_telemetry()` 匹配
`wo.com.cn` / `guardprovider` / `antifraud` / `telemetry` / `beacon` /
`analytics` / `upload` 等关键词，按设备+域名聚合，输出线索类型。

> 当前实测：`suspects = 0`、`telemetry = 19`（含
> `telemetry.example-vendor.com`、`beacon.example-sdk.com` 等）、`watch = 12`。
> **0 条疑似是真实结论**，不是阈值写错：库里短时上行连接最多的一台也只有 5 次。
> 没有为了「看起来有结果」放宽阈值制造误报。

### 判读原则

1. 「上行次数多」和「目的域名反复出现」两条证据要一起看；
2. 结合客户端详情里的常访域名与查询日志，确认是否发生在息屏/无操作时段；
3. 界面明确写「疑似，需人工核实」，程序**不执行任何处置动作**，
   不卸载组件、不改 hosts、不改防火墙。

## 三、移动端与文案

- 窄屏（≤760px）表格自动转**卡片**：JS 从 `.rhead` 提取表头文字写入
  `data-label`，CSS 每格显示「标签 + 值」，**一列都不隐藏**。
  新增视图无需改行生成代码，`labelizeRows()` 统一处理。
- 界面禁用内部术语：`小时桶` → `按小时统计 · 共 N 小时`、
  `/ 桶` → `最忙一小时 N 次`、`峰值` → `实测最快`、
  `窗口` → `所选时段`、`指纹` → `规则版本`、`模式` → `规则条目`。
- HTML 加了 `no-store` 与版本戳（页脚可见）。若仍看到旧文案，
  强制刷新一次（Ctrl+F5 / Cmd+Shift+R）即可。
